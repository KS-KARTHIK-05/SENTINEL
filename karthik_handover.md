## 2. What the paper is now about
**Title:** *Information-Triggered Delivery for Timely Victim Reporting in Infrastructure-Free UAV Search and Rescue*
**Authors (as in `main.tex`):** Karthik KS, Nicholas Christo T, Balaji Ganesh Rajagopal

**Main idea.**
- The old paper's goal was to keep the swarm connected at all times.
- Our experiments showed that this lowers how quickly victims get reported.
- So the new paper optimises **timely reporting**: a victim counts only if the responder receives the report within 60 s of its first detection.

**Contributions (as stated in Section I):**
1. **Information-triggered delivery (Amendment A1).** Each UAV searches freely. When it holds a confirmed victim that the responder has not received, it switches to DELIVER mode and carries the report back to the responder's network. The hold time T_hold controls the trade-off between discovery and delivery.
2. **Corroborative multi-view fusion (Amendment A3).** Views of a victim from several UAVs are combined so that occluded or blocked views cannot veto a clear one. The earlier naive-Bayes fusion penalised occluded views.
3. **Link-preservation safety layer with proofs.** It uses an LMST neighbour set and a midpoint-ball projection that accounts for staleness and obstruction:
   - Lemma 1: the old nearest-neighbour rule does *not* imply connectivity;
   - Lemma 2: the LMST contains the MST;
   - Proposition 1: link preservation;
   - Corollary 1: the delivery component stays connected;
   - Proposition 2: a union bound under fading;
   - Proposition 3: an exposure bound.
4. **A reproducible evaluation:**
   - 11 experiments, about 11,000 simulated missions, 30 seeds each;
   - 7 baselines, all tuned with the same budget;
   - paired Wilcoxon tests with Holm correction;
   - a cross-check in PX4/Gazebo.

**Framing (Amendment A2, evidence-led).**
- The ablation shows what actually produces the gains: fusion and the delivery trigger.
- The connectivity spring, LMST and projection have **no significant effect on the reporting rate**, so we present them as a *safety property*, not as a performance gain.
- Keep this honesty. It protects the paper against the "incremental" criticism.

The YOLO detector is **not claimed as a contribution**. It is an enabling component, and we evaluate it because Reviewer 1 asked for YOLO26.

**Problems we found ourselves (also documented):**
- **Wrong citations in the old paper.** HIT-UAV was credited to the wrong authors; the correct reference is Suo et al., *Sci. Data* 2023. The symmetry-informed MARL paper had the wrong first author; it is Shi et al., *IEEE TMC* 2025. Several other references did not match the text. All 23 references in the new paper were checked; see `docs/related_work_notes.md`.

  - naive-Bayes fusion penalised occluded views (Amendment A3);

## 6. How to run the simulation (one command)
This runs on the lab workstation (i7-12700, RTX 3060, Ubuntu 22.04, ROS 2 Humble, Gazebo Harmonic, PX4).

```bash
~/sentinel_ws/run_sentinel_demo.sh
```
- Gazebo opens with the 100 m disaster world and **6 drones**, and the SENTINEL stack starts with YOLO26n.
- Two viewers open: the thermal camera with YOLO boxes, and the ROS node graph.
- The drones take off after about 20 s and the terminal prints a status line every 10 s.
- **Stop with Ctrl-C.**

| Option | Meaning |
|---|---|
| `-n 3` | number of drones (default 6; 9 at most on this PC) |
| `-w sentinel_d25_s0` | another world (this one is the old 25 m v1 scene) |
| `-p model` | calibrated detector model instead of YOLO26n (drones without cameras; lighter) |
| `--no-crash` | no injected UAV failure |
| `--headless` | no Gazebo window |

- Manual three-terminal steps and the commands that reproduce every number are in `docs/RUN_GUIDE.md`.
- If a run left processes behind, close all terminals and run the command again; the launcher cleans up its own process group.

### Rules for the restructuring (please keep these)
1. **No hand-typed numbers.** Every number must exist in `docs/RESULTS.md` or a generated table. If you change a number in the text, check it there first.
2. **No overclaiming.**
   - Use "guarantee" only where a proposition backs it.
   - Severe channel and 200 m N = 10–20 are "ahead or tied", not wins.
   - Make no Jetson or edge-speed claim; we have no Jetson measurement.
   - Run `python3 scripts/lint_language.py` before you send the paper anywhere.
3. **Keep the null results** (spring, LMST and projection not significant; MAPPO close in dense swarms). They are what makes the paper believable.
4. **Keep the method and theory as the core** (R1.3). Implementation stays short.
5. **New citations:** add one only after checking it against its DOI or arXiv ID, and note it in `docs/related_work_notes.md`.
